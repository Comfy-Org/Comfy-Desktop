# Desktop redesign: decision log

Product and engineering decisions taken while implementing [the plan](desktop-redesign-plan.md) without a product review. Each entry says what was decided, why, and how to reverse it. Review them; anything marked **Revisit** is a judgement call worth a second opinion.

## Process

| # | Decision | Why |
| --- | --- | --- |
| P1 | The plan is cut from 44 PRs to 19 (M1 5, M2 9, M3 5). Each commit on `PabloWiedemann/desktop-redesign` is one planned PR, in order. | Asked for about half. A PR now covers one surface or one data domain. |
| P2 | Work branches from `origin/main` (last rebased onto `195ae80a`), in a separate worktree. The prototype branch is untouched and still uncommitted. | Start clean; keep the prototype as the visual reference. Push the prototype branch before the team reviews, or the plan's references are not reachable. |
| P3 | Each commit is one pull request, stacked: each PR is based on the one before it, so it shows only its own change. | One reviewable change per PR, merged in order. |
| P4 | E2E tests are not run locally. | On macOS the harness overwrites the real `~/Library/Application Support/comfyui-desktop-2`. They run in CI. |

## Milestone 2: Builds dashboard

| # | Decision | Why | Reverse by |
| --- | --- | --- | --- |
| M2.1 | The rollout flags (`newDashboardEnabled`, later `breadcrumbTitleBarEnabled`) are not defaulted settings. Their defaults live in `ROLLOUT_DEFAULTS` (`settings.ts`) and are read through `isRolloutEnabled`; main passes them to renderers in the URL query (`src/shared/rolloutFlags.ts`), so a change applies on the next window load. Neither appears in Desktop Settings. | `settings.set()` writes `defaults` to disk, which would pin `false` for existing users and stop a launch reaching them. | — |
| M2.2 | The sidebar foot shows the selected workspace and the account email. Its menu follows platform.comfy.org's: the workspace (plan • role; opens the workspace list, with Add workspace), Manage plan & credits (owners only), the email, Language and Log out. Plan & credits and Add workspace open Comfy Cloud's own pages in the browser. The prototype's usage, limits, people and provider-key entries are left out. | Desktop has no data or screens for those; the ones kept have a real destination. | Remove an entry and its `openCloudPage` page. |
| M2.3 | Workspace avatars reuse the existing `DevPlatformAvatar` (deterministic gradient per name) rather than the prototype's solid colour squares. | Real identity already used elsewhere in Desktop; the prototype's colours were mock data. | — |
| M2.4 | Signed out, the sidebar foot is the prototype's "Log in to Comfy" card. | Matches the prototype; signing in is the only action. | — |
| M2.5 | All builds cards carry every state of the M1 tiles (update, migrate, error, problem tag, TRY FREE, Why try Cloud, kebab) through one shared `InstallBadges` component and `useInstallTileState`; the lifecycle status moves to the card's status line, as in the prototype. Cards show no model or node counts and no start-time estimate; their footer shows the install's meta line (channel, version or source). | No duplicated state logic; counts would need a scan per card, and estimates cannot be computed. | — |
| M2.6 | Status line wording: **Running**, **Starting…**, **Stopping…**, **Updating…**, **Error**, otherwise **Not running** — except Comfy Cloud, which reads **Ready**. | A cloud build has no local process; "Not running" would read as broken. **Revisit** the word. | Change `idleStatusKey`. |
| M2.7 | Remote builds appear under **All** only, with the laptop mark; their server is named in the build page's tag tooltip. | The prototype has no Remote filter; adding one is a design change. | Add a `remote` filter option. |
| M2.8 | The card click opens the build page; only the card's button (Start/Open ComfyUI) launches. The build page's kebab and the card's kebab open the existing context menu (Manage, Update, snapshots, folder, delete, …), positioned at the pointer. | Same actions as today; the prototype's dropdown would need a second menu definition. | — |
| M2.9 | **Stop** shows on the build page for running *local* builds only, and goes through the existing confirm. | Cloud and remote builds have no local process to stop. | — |
| M2.10 | Local builds are listed from their files (workflows folder, model roots and `extra_model_paths.yaml`, `custom_nodes`), not ComfyUI's asset database. | `--enable-assets` is still off by default (opt-in through v0.41.2, and on master since 12 Oct 2026); files work whether ComfyUI runs or not. | Read `/api/assets` on running builds once the database is on by default. |
| M2.11 | Comfy Cloud is listed through its API with the desktop's Cloud session token: workflows from `/api/userdata`, models from `/api/assets?include_tags=models`. Verified against a real account on 17 Oct 2026. Cloud models have a filter row: All (own plus the public library), My models (`include_public=false`) and Public models (the public library only, kept by `is_immutable`). | Cloud has no per-build model folder, so a build page shows both what the workspace uploaded and what Cloud provides, with a way to tell them apart. | Change the filters in `listCloudModels`. |
| M2.12 | Listings read at most 5,000 entries and 8 folder levels, then filter, sort and page (100 per page, at most 500). | Large model folders must not stall the dashboard; estimates are not allowed. | Change `MAX_LISTED_ENTRIES` / `MAX_WALK_DEPTH`. |
| M2.13 | Remote builds list nothing; their tabs show an empty state. Comfy Cloud's custom nodes are "managed" (no list). | A remote server's files are not on this computer; Cloud pre-installs its node packs. | Query the remote server's API in a follow-up. |
| M2.14 | `comfy-media://` serves local image, video and audio files only from the build's resolved **output** and **input** folders (after a real-path check), and Comfy Cloud assets by id through `/api/assets/<id>/content`. The Cloud request uses Node's `fetch` so the redirect to signed storage is followed by hand, without the token, and only to `https`. Byte ranges are passed on and responses carry `nosniff`. It is registered on the default session only; it answers 404 for everything while the dashboard is off. **Security review this PR.** | The panel CSP blocks `file://` and authenticated Cloud URLs; Electron's `net.fetch` rejects manual redirects. | — |
| M2.15 | The Assets tab lists images, video and audio. Local: output and input folders, newest first, keeping the newest 5,000 of up to 50,000 files read (a folder shared by both is listed once; the default shared output means every local build shows the same outputs). Cloud: the workspace's **outputs** (`include_tags=output`), named by file name without their sub-folder; other file types are skipped, so Cloud counts are not shown. | Matches where ComfyUI writes; Cloud has no "any tag" filter in every deployment. | Include `input` for Cloud with `tags_any` once it is supported everywhere. |
| M2.16 | Clicking a local asset reveals it in the OS file browser (`install-contents:reveal-asset`, same folder check); Cloud assets are view-only. | No local file to reveal for Cloud. | — |
| M2.17 | Workflows are a list, not cards with the prototype's graph thumbnail. Opening a workflow starts (or opens) its build; it does not open that workflow. | Workflows carry no preview image and the prototype's graph is generated from mock data; ComfyUI has no way to be told to open a given saved workflow yet. | Add a frontend hook, then pass the workflow path on launch. |
| M2.18 | Long lists page with a **Load more** button, not infinite scroll. | Accessible and predictable; no scroll observers. | — |
| M2.19 | The build page opens on **Workflows**. Tab labels carry no counts; the Models filter row shows counts once loaded. | Counts on tabs would need every listing loaded up front. | — |
| M2.20 | The Assets tab has a type filter (all / images / video / audio), search and sort (newest / name); no multi-select or bulk actions. The type filter is the listing's `filter`, applied in main before paging; Cloud pages can come back short because Cloud cannot filter by media kind. Videos show their first frame (`preload="metadata"`). | The prototype's bulk Download / Move / Delete have no real counterpart yet. | Add bulk actions with their IPC. |
| M2.21 | **The rename reaches every user-facing surface, the install wizard, progress and first-run screens included**, not only the screens restyled in M1. 146 strings in en and zh: "instance" → "build" (实例 → 构建), and a handful of hardcoded English dialog titles in main. Kept as "instance": a running ComfyUI process or another Desktop app (port-conflict errors, "Connect to a running ComfyUI instance"). "Legacy Desktop instance" becomes "Legacy Desktop install". This **reverses the plan's** "wizard keeps instance until redesigned". | Otherwise "New build" on the dashboard opens a wizard titled "New Instance": one concept needs one word. | Revert the out-of-scope namespaces (`newInstall`, `progress`, `firstUse`, `track`, `loadSnapshot`, `migrate`) in `locales/en.json` and `locales/zh.json` to their pre-`feat(dashboard): launch the Builds dashboard` text. |
| M2.22 | The Developer Platform action "Create Build" (promote a local build to a workspace) becomes **Add to workspace**, with "Make this build available to your workspace in Comfy Developer Platform." as its hint; "This install is not linked to a build." becomes "This build is not linked to a workspace release." (both places it appears) | "Create Build" on something already called a build reads as a duplicate. **Revisit** with the Developer Platform team. | Restore `devPlatform.workspace.promoteToWorkspace*`, `newInstall.errorNoBuild` and `comfybuilder.errorNoBuild`. |
| M2.23 | The Builds dashboard is on by default (`ROLLOUT_DEFAULTS.newDashboardEnabled = true`); setting `newDashboardEnabled: false` in `settings.json` brings back the original dashboard for one release. The e2e harness seeds `false` so the existing suites keep testing the dashboard they were written for; `e2e/builds-dashboard.test.ts` covers the new one. **E2E not run locally** (macOS harness writes into the real profile). | A launch must reach existing users; rewriting every e2e suite for the new dashboard is out of scope. | Set the default back to `false`. |

## Milestone 3: breadcrumb title bar

| # | Decision | Why | Reverse by |
| --- | --- | --- | --- |
| M3.1 | With `breadcrumbTitleBarEnabled` on, **every** launch opens or focuses the build's own window: from the dashboard (cards, build page, post-operation Open) and from the instance picker in any window (the navigation matrix turns "switch" into "open in its own window"). The dashboard window never turns into a build and never closes itself after a launch. First-use auto-launch still launches in place. | One rule is easier to learn than "new window from here, same window from there". The first-use flow is out of M3's scope. | Narrow `inOwnWindow` in `navDecision.ts` to `currentView === 'dashboard'`. |
| M3.2 | The flag reaches the panel and the title bar in their URL query (re-read on every load), and the instance picker in its snapshot (`ownWindows`). It is on only when `newDashboardEnabled` is on too. | No async settings read before first paint; popups have no `getSetting`. | — |
| M3.3 | The breadcrumb is built with the title bar's own button styles, not design-system utilities, and the build crumb shows the install-type icon rather than the `LocationIcon`. Refresh and the app menu move to the right end. | A build window's bar takes ComfyUI's colours, light or dark; the title bar's styles already handle both, the Void tokens do not. | — |
| M3.4 | The breadcrumb's chevron takes over the centre pill's element role: it anchors the onboarding coachmark ("Switch & manage builds") and the popup, and the install update chip sits right after the build crumb. During first-use lockdown the original static bar shows. | Keeps every pill duty without new plumbing. | — |
| M3.5 | The chevron opens a **build switcher**, not the instance picker: All builds, then the builds with a window open, then the others by last use, then Manage builds. Each row shows the build's type icon, a status dot, its state ("Running", "Not running", "Ready" for Cloud) and when it was last used, or "Current". Picking a build opens or focuses its own window; Manage builds and All builds focus the dashboard. | The prototype's switcher. The instance picker stays reachable from the info card's "Settings & updates". | Point the chevron back at `handleInstallPillWithCoachmark`. |
| M3.6 | Hovering the build's name for 350 ms (or clicking it) opens its **info card**: name, type, status, ComfyUI version, location (home folder as `~`, Cloud's host, or the remote server), last used, an available update, then Settings & updates, Open folder (local builds) and Close window. It closes 250 ms after the pointer has left both the name and the card. The card takes focus like any title-bar menu, so Escape closes it. | Matches the prototype's hover card. The prototype's "Couldn't start" fact is left out: Desktop does not keep a last launch error per build. | — |
| M3.7 | Both menus are rows of the existing title-bar menu popup (`kind: 'menu'`), composed in main (`popups/buildMenus.ts`) with icons, headings, status dots and second lines, rather than new popup kinds. Main echoes which menu opened (`menuId`) so the title bar never confuses two opens in a row. They are read when they open and do not update while open; a long switcher scrolls inside the window. | Reuses the popup's open, dismiss, focus and sizing; a menu is open for seconds. | — |
| M3.8 | With builds in their own windows, opening a build from a build window launches it through the dashboard window (opening one only if none exists) instead of a new empty chooser window. | Otherwise the new chooser window launches the build into yet another window and stays behind, empty. | — |
| M3.9 | The breadcrumb title bar ships **on**, with the Builds dashboard. `breadcrumbTitleBarEnabled: false` brings back the centre pill and in-place switching for one release; turning the dashboard off turns the breadcrumb off too. The e2e suites written for the original dashboard keep running against it (the harness seeds `newDashboardEnabled: false`); `breadcrumb-title-bar.test.ts` covers the new bar. **E2E not run locally** (macOS harness writes into the real profile). | Same escape-hatch pattern as the dashboard launch (M2.23). | Set the default back to `false` in `ROLLOUT_DEFAULTS`. |
